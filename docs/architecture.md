# Архитектура

## Что это

Пассивный мониторинг OpenVPN-сервера: журнал сессий с геолокацией, учёт
сертификатов/CRL/CCD, REST API и веб-интерфейс. Система **только наблюдает** —
она не управляет VPN, не выдаёт и не отзывает сертификаты.

## Компоненты

```
OpenVPN ──(script-hooks)──> collector ──> MySQL <── web (FastAPI + Jinja2)
   └──(management socket)──> collector
```

- **`collector/`** — запись данных. Два независимых пути:
  - **Хуки** `client_connect.py` / `client_disconnect.py` вызывает сам OpenVPN на
    каждое (от)подключение через `client-connect`/`client-disconnect` в server.conf.
    Читают переменные окружения OpenVPN, пишут в БД.
  - **Периодический синк** `sync_all.py` (systemd timer `openvpn-sync.timer`)
    выполняет по порядку `cert_sync` → `crl_checker` → `ccd_checker` →
    `session_cleanup`. Порядок важен (инвариант S3.2).
  - `mgmt_client.py` — чтение management-сокета OpenVPN (список живых клиентов
    для обнаружения orphaned-сессий).
- **`core/`** — общий код: `models.py` (SQLAlchemy), `database.py`, `config.py`,
  `geoip.py`, `serial.py`.
- **`web/`** — FastAPI: `api/{accounts,sessions,attempts,stats}.py` под `/api/v1`,
  `routes/pages.py` (HTML-страницы), `auth.py`, `schemas.py`.
- **`database/`** — Alembic (`migrations/`) и `init.sql` для ручного bootstrap.

**Границы**: collector пишет, web API читает, БД — единственное хранилище
состояния. Список инвариантов — [invariants.md](invariants.md).

## Почему хуки, а не разбор логов

Исходно рассматривался вариант с демоном, следящим за `openvpn-status.log` и
серверным логом. Выбраны script-hooks, и это решение стоит понимать, прежде чем
пытаться его пересмотреть:

| Разбор логов | Script-hooks |
|---|---|
| Формат лога меняется между версиями OpenVPN, парсер хрупкий | Переменные окружения стабильны и документированы |
| Задержка до следующего цикла чтения | Событие фиксируется в момент подключения |
| Нужно дедуплицировать уже обработанные строки | Каждое событие приходит ровно один раз |
| Отдельный процесс-демон, который может незаметно умереть | Исполнение гарантирует сам OpenVPN |

Плата за это — **жёсткое требование exit 0** (инвариант I4.5): ненулевой код
возврата из `client-connect` заставляет OpenVPN отклонить подключение клиента.
Поэтому хуки перехватывают все ошибки, включая сбои на этапе импорта.

Management-сокет используется только для чтения списка подключённых клиентов —
это единственный надёжный способ узнать, кто реально онлайн, когда отключение не
было зафиксировано хуком (падение сервера).

## Учёт неудачных попыток — не реализован

Таблица `connection_attempts`, API `/api/v1/attempts` и страница «Attempts»
существуют, но **в таблицу никто не пишет**: ни один компонент её не заполняет.
Страница всегда пуста. Для заполнения нужен разбор серверного лога OpenVPN
(TLS-ошибки, отзыв, истёкший сертификат) — от `tls-verify`-хука для этого
сознательно отказались, чтобы не вмешиваться в процесс аутентификации VPN.

## Конфигурация

`core/config.py` — единая точка: YAML из `config/*.yaml` плюс ENV-override поверх.
`DATABASE_URL` перекрывает подключение целиком. Файлы конфигурации **не
обязательны**: если все значения заданы через ENV, приложение работает без них
(так устроен Docker-стенд). При отсутствии обязательных значений — падение с
`ConfigError`, fallback на захардкоженные пароли запрещён.

Конфиг кешируется через `lru_cache`; в тестах после смены ENV вызывать
`core.config.reload_config()`.

⚠️ `core/database.py` создаёт engine и `SessionLocal` на этапе импорта, поэтому
`DATABASE_URL` должен быть выставлен ДО первого импорта. В тестах это делает
корневой `conftest.py`.

## Схема БД: несколько источников правды

Схему описывают `core/models.py`, миграции Alembic и `database/init.sql`.
Канон — **миграции**. `docker/mysql/init.sql` намеренно НЕ создаёт таблицы
(только `ALTER DATABASE`): раньше он конфликтовал с `alembic upgrade head` и
web-контейнер уходил в crash-loop с «Table already exists».

Любое изменение схемы — согласованно во всех местах.

## Тесты

Юнит- и интеграционные тесты идут на SQLite, прод — MySQL. Это значит, что
расхождения по UNSIGNED/ENUM/FK локально не ловятся; единственная проверка на
настоящем MySQL — Docker-стенд. Модели намеренно используют обычный `Integer`
вместо UNSIGNED ради совместимости с SQLite.
