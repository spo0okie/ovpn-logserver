# Несколько сертификатов на пользователя

## Модель

**Единица учёта — сертификат, а не человек.** Одна строка `accounts` = один
сертификат. «Пользователь» — это множество строк с одинаковым `cn`.

Уникальность: `uk_cn_serial (cn, serial_number)`. Раньше был `uk_cn` по одному
`cn`; его удалила миграция `002_add_serial_number`. Причина перестройки — при
перевыпуске сертификата система падала с `Duplicate entry '<cn>' for key
'accounts.uk_cn'`.

Следствия для API: список `/api/v1/accounts` группирует по `cn` и не отдаёт `id`
аккаунта; ключ детальной страницы — `cn`, а не `id`; сессии пользователя
собираются по `account_id IN (все сертификаты этого CN)`.

## Серийные номера

**Канон — decimal-строка.** Приведение только через `core.serial.normalize_serial()`.

Источники расходятся между собой, и это главная ловушка:

| Источник | Формат |
|---|---|
| OpenVPN `tls_serial_0` | decimal (в 2.4+); в старых версиях — hex с двоеточиями |
| `cryptography.x509.serial_number` | int |
| Исторические записи в БД | вперемешку |

Прямое сравнение без нормализации плодит дубли accounts и ломает отзыв.
Читать надо именно `tls_serial_0` (не `tls_serial`) — иначе multi-cert не работает.

### Особые значения

- **`legacy_<id>`** — записи, доехавшие с домиграционной схемы. Миграция 002
  заполнила их через `CONCAT('legacy_', id)`, чтобы старые строки не нарушили новый
  composite unique. Реальный серийник у них неизвестен, поэтому `crl_checker`
  обязан их **пропускать**: иначе отзыв применится не к тому сертификату.
  `normalize_serial()` намеренно возвращает такие значения без изменений.
- **`unknown`** — валидное значение, а не ошибка: `client_connect` получает его,
  когда OpenVPN не отдал `tls_serial_0`. Колонка сделана NOT NULL с
  default `'unknown'` вместо nullable, чтобы composite unique работал (в MySQL
  NULL не участвует в уникальности).

## Может ли пользователь подключаться

Правило: есть хотя бы один сертификат с `is_revoked = False` И (`valid_to IS NULL`
ИЛИ `valid_to >= now`). Отзыв одного сертификата не делает пользователя неактивным.

⚠️ Логика продублирована в трёх местах — при правке менять все три:
`core.models.Account.can_user_connect`, `web.api.accounts._can_user_connect` и
инлайн-агрегат в `list_accounts`.

Обратите внимание: `valid_to IS NULL` считается **активным**. Пустые даты
появляются, когда аккаунт завёл хук при подключении, а `cert_sync` до него не
добрался (например, каталог сертификатов настроен неверно).

## Гонки и откат

- **`cert_sync` × `client_connect`**: оба могут вставить одну и ту же пару
  `(cn, serial)`. `cert_sync` ловит `IntegrityError` и переходит на update.
  Обработка каждого сертификата коммитится отдельно — иначе один конфликт
  откатывал бы весь батч синхронизации.
- **`downgrade()` миграции 002 исполним не всегда**: восстановление `uk_cn`
  упадёт, если в базе уже есть несколько сертификатов на один CN. Откат возможен
  только на данных без дублей CN.
