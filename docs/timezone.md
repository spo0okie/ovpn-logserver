# Время и часовые пояса

## Контракт

**В БД всё хранится в naive UTC.** Конвертация в локальную зону — исключительно на
границе отображения. Ничто ниже web-слоя часовыми поясами не занимается.

Отображение — через `web/utils/timezone.py`:

- `format_datetime()` трактует naive datetime как UTC (`replace(tzinfo=timezone.utc)`) —
  это допущение и есть связующее звено с naive-хранением. Формат по умолчанию
  `%Y-%m-%d %H:%M`.
- Зона берётся из системы сервера через `tzlocal`, не из конфига и не из профиля
  пользователя: она одна для всех пользователей. `tzlocal` кеширует зону в
  процессе, поэтому смена TZ хоста подхватится после перезапуска web.
- Функция принимает и `datetime`, и ISO-строку: шаблоны получают данные двумя
  путями — напрямую из ORM (datetime) и через pydantic-схемы API (строка). Отсюда
  ветвления `{% if x is string %}` в шаблонах.
- `format_datetime(None)` падает с `AttributeError` — вызовы обязаны быть под
  `{% if %}`.

В Jinja2 подключено как фильтр `local_datetime` (`web/routes/pages.py`).

## Единый источник времени

Всё, что пишется в БД и сравнивается с ней, берёт время через
[`core/time.py`](../core/time.py):

```python
from core.time import utcnow, utcfromtimestamp
```

`utcnow()` возвращает **naive UTC** — ровно то же, что давал `datetime.utcnow()`,
но без устаревшего вызова (`utcnow` объявлен deprecated с Python 3.12).

Прямая замена на `datetime.now(timezone.utc)` была бы ошибкой: она даёт
**aware**-время, а его сравнение с naive-значениями из БД кидает `TypeError`.
Именно так в проекте когда-то и появилось смешение стилей.

**Исключение — `web/auth.py`.** Файловые сессии не касаются БД, полностью
самодостаточны и работают с aware-временем. Смешения не возникает, переводить их
не нужно.

Колонки с `server_default CURRENT_TIMESTAMP` в миграциях сохранены как страховка
для записи мимо ORM, но фактически не срабатывают: и ORM, и сырые пути
(`INSERT ... ON DUPLICATE KEY UPDATE` в `client_connect`, upsert сервера в
`collector/server_registry.py`) задают время явно.

⚠️ Ручной SQL — исключение: `UPDATE sessions …` (например, бэкфилл `server_id`
из [multisite.md](multisite.md)) запускает `ON UPDATE CURRENT_TIMESTAMP`, а он
пишет время сессии MySQL, которое не обязано быть UTC. Это касается только
`updated_at`, на журнал не влияет.

## Таблица сессий: время приходит готовым

Страница `/sessions` рендерится клиентским DataTables через AJAX, и серверный
Jinja-фильтр к таким данным неприменим. Поэтому API отдаёт рядом с UTC-полями
**предформатированные** `connected_at_local` и `disconnected_at_local`
(`web/api/sessions.py`), а таблица и CSV-экспорт показывают именно их. Зона
везде одна — серверная, как на остальных страницах. Сырые `connected_at` /
`disconnected_at` (UTC) остаются в ответе: по ним идут сортировка и фильтры
на сервере.
