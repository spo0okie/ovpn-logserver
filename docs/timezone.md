# Время и часовые пояса

## Контракт

**В БД всё хранится в naive UTC.** Конвертация в локальную зону — исключительно на
границе отображения. Ничто ниже web-слоя часовыми поясами не занимается.

Отображение — через `web/utils/timezone.py`:

- `format_datetime()` трактует naive datetime как UTC (`replace(tzinfo=timezone.utc)`) —
  это допущение и есть связующее звено с naive-хранением. Формат по умолчанию
  `%Y-%m-%d %H:%M`.
- Зона берётся из системы сервера через `tzlocal`, не из конфига и не из профиля
  пользователя. Смена TZ хоста меняет отображение сразу у всех.
- Функция принимает и `datetime`, и ISO-строку: шаблоны получают данные двумя
  путями — напрямую из ORM (datetime) и через pydantic-схемы API (строка). Отсюда
  ветвления `{% if x is string %}` в шаблонах.
- `format_datetime(None)` падает с `AttributeError` — вызовы обязаны быть под
  `{% if %}`.

В Jinja2 подключено как фильтр `local_datetime` (`web/routes/pages.py`).

## Не смешивать naive и aware

`datetime.utcnow()` (naive) и `datetime.now(timezone.utc)` (aware) при сравнении
дают `TypeError`. Сейчас в коде смешанный стиль: `web/auth.py` использует aware,
почти всё остальное — naive. При правках придерживаться стиля окружающего кода.

Отдельный источник расхождения: часть колонок имеет client-side default
`datetime.utcnow` в моделях и одновременно `server_default CURRENT_TIMESTAMP` в
миграциях. Запись мимо ORM получит время сервера БД (в его локальной зоне), запись
через ORM — UTC. Пока не унифицировано.

## Незакрытая часть

Страница `/sessions` — самая нагруженная временем — **показывает сырой UTC**.
Таблица рендерится клиентским DataTables через AJAX, а серверный Jinja-фильтр к
таким данным неприменим в принципе. Чтобы закрыть, нужен один из вариантов:

- JS-конвертация в `render`-функции колонки DataTables;
- либо предформатированное поле от API.

Это не забытая мелочь, а сознательно незакрытая часть задачи — см.
[known-gaps.md](known-gaps.md).
