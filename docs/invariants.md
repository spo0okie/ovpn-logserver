# Каталог инвариантов

Коды вида `I4.5`, `C1.7`, `M1.4`, `S3.2` встречаются в докстрингах и тестах по всему
коду (около 40 файлов). Этот файл — их единственная расшифровка: если код ссылается
на инвариант, смотреть сюда.

Формулировки приведены в соответствие с фактическим поведением кода. Там, где
исходный инвариант устарел после переработки, это отмечено явно — старую
формулировку не восстанавливать.

## Сквозные правила

- REST API версионирован (`/api/v1/`), ответы JSON, пагинация `page`/`per_page`,
  мета-информация в `meta`.
- **Границы модулей**: collector пишет в БД, web API читает из БД. БД — единственное
  хранилище состояния.
- Время в БД — **naive UTC**. Конвертация в локальную зону только на границе
  отображения (см. [timezone.md](timezone.md)).
- Статусы сессий: `active`, `closed`, `error`.
- Типы ошибок подключения: `auth_failed`, `cert_revoked`, `cert_expired`,
  `ccd_missing`, `tls_error`, `other`.

## M1 — клиент Management Interface

| Код | Инвариант |
|---|---|
| M1.1 | Самостоятельный модуль с собственными тестами |
| M1.2 | Путь к сокету берётся из конфигурации, не захардкожен |
| M1.3 | Возвращает `Set[str]` — CN активных клиентов |
| M1.4 | При любой ошибке сокета возвращает **пустое** множество |

Ответ команды `status 3` разбирается строго по табуляции: CN может содержать
пробелы, и split по пробелам даёт неверный CN. Перед закрытием сокета отправляется
`quit`.

**Неполный ответ = ошибка.** `_recv_until_end()` возвращает `(buf, complete)`;
если маркер `END` не получен (таймаут, обрыв, переполнение буфера), ответ считается
неполным и наверх уходит пустое множество. Частичный список клиентов опаснее
пустого: он выглядит достоверным и приводит к закрытию живых сессий.

| Код | Инвариант |
|---|---|
| S3.1 | `session_cleanup` выполняется ПОСЛЕ остальных синков |
| S3.2 | `session_cleanup` выполняется ТОЛЬКО если предыдущие шаги прошли без ошибок (учитывается и `stats['errors'] > 0`, а не только исключения) |

## Почему очистка сессий устроена именно так

Три уровня защиты выше (M1.4 → C1.7 → S3.2) — не перестраховка, а условие
корректности. Разбирающему код важно понимать:

- **Пустой ответ mgmt никогда не означает «никто не подключён».** Сокет мог быть
  недоступен или перезапущен. Тот, кто «упростит» fail-closed, разом пометит
  `error` все живые сессии.
- **`snapshot_time` закрывает гонку с `client-connect`.** Снимок mgmt берётся ДО
  выборки сессий, и трогаются только сессии старше снимка. Иначе клиент,
  подключившийся между опросом mgmt и запросом к БД, был бы сразу закрыт как
  orphaned. Остаточное окно всё же есть: `connected_at` берётся из `time_unix`,
  то есть времени начала подключения, а не вставки строки.
- **Два механизма закрытия orphaned нужны оба**: периодический (`session_cleanup`
  по таймеру) ловит падение сервера, синхронный (`client_connect`) мгновенно
  чистит дубль при переподключении того же аккаунта.
- **Семантика статусов**: `closed` — штатное отключение через хук, `error` —
  сессия оборвалась и отключение не зафиксировано. Сессия без связанного account
  считается orphaned сознательно.
- Обнаружение orphaned — часть нормального потока, а не ошибка: `client_connect`
  при этом обязан вернуть exit 0 (I4.5).
